# NexaMart autonomous visual-to-functional delivery protocol

## Owner rules (2026-09-17)
1. Use multiple non-overlapping agents to drive every customer, seller, admin, and auth route to strict reference-matched visual UI/UX parity. Do not accept a superficially similar surface.
2. Frontend visual parity is first. Only after a visual control/composition is complete, trace it to its required server contract and implement the minimum truthful backend workflow.
3. Never leave the cycle idle while approved work remains: parent-verify a bounded slice, then launch the next safe non-overlapping slice immediately.
4. Context engineering is mandatory. Every agent reads `PRODUCT_CONTEXT.md`, `DESIGN_CONTRACT.md`, `DELIVERY_LEDGER.md`, `VISUAL_PARITY_MANDATE.md`, this protocol, `CODEX_PROGRESS.md`, and current source before selecting or modifying a slice.
5. Completion means reference-matched desktop and narrow-mobile composition, keyboard/accessibility states, real loading/error/empty/pending states, focused RED→GREEN evidence, parent-owned full gates, and rendered screenshot inspection. A static/source-only pass is not visual completion.
6. The user authorizes necessary local development migrations, seeds, and setup. Before applying any migration/seed, inspect the exact target, migration history, backup/rollback feasibility, and scope; apply only the required change and verify readback. Never use credentials, deploy, or mutate production without explicit target/access verification.

## Truth boundaries
- Preserve original NexaMart branding, monogram, truthful copy and live API data.
- Do not copy a third-party reference brand, proprietary copy/assets, or fabricate metrics, reviews, payment, delivery, carrier, SLA, tracking, recommendations, or provider claims.
- Visible frontend controls require an API-backed contract; no frontend-only business logic or fake success.
