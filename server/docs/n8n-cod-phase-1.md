# COD Phase 1 implementation note

The existing order lifecycle is `pending → confirmed` or `cancelled`. Each multi-seller order line has `pending → processing → packed → shipped → delivered`; legacy lines also allowed cancellation and a direct delivered-to-returned path. Payment originally had only `unpaid`. Checkout already persists a customer order event and line events. Sellers own lines, while Admin has global order oversight.

COD needs a payment method, line-level collection evidence, failure and return request states, a protected callback, and a durable outbound event record. `shipped` is the existing dispatch state. Order status remains the existing order-level state. The new line path is `pending → processing → packed → shipped → delivered` with collection on the same transaction; or `shipped → failed_delivery → return_requested → returned`. Cancellation remains possible before dispatch. Order payment becomes `collected` only after all lines are delivered with collection timestamps. Existing checkout requests safely default to COD and may explicitly send `paymentMethod: "cod"`; no existing order is rewritten during checkout.

Staff uses `PATCH /api/cod/order-items/:orderItemId` with `{ "action": "..." }`; Seller scope is enforced by line ownership and Admin has global authority. Admin confirms via `POST /api/cod/orders/:orderId/confirm`. The existing `PATCH /api/seller/order-items/:orderItemId/fulfillment` is wired to the COD transaction in the app. Local n8n uses `POST /api/cod/local/callback` with `{ "eventId", "orderItemId", "action" }`, where action is `cod.delivery_collected`, `cod.delivery_failed`, or `cod.return_requested`. `GET /api/cod/local/pending-confirmation` feeds reminders and `POST /api/cod/local/dispatch` explicitly sends due outbox records. All local endpoints require a dedicated bearer service token. The callback is idempotent by unique external event ID.

The persisted outbound event payload contains exactly `eventId`, `eventType`, `occurredAt`, `orderId`, `reference`, `sellerId`, `amount`, `currency` (`BDT`), `orderStatus`, `paymentMethod`, and `paymentStatus`. No address or customer identity is sent. The dispatcher signs timestamp and raw JSON with HMAC SHA-256. Events are `cod.order.created`, `cod.order.confirmed`, `cod.order.dispatched`, `cod.order.delivered_collected`, `cod.order.delivery_failed`, and `cod.order.returned`. Failed dispatches retry on later manual calls, up to five attempts.

For local setup, see [automation README](../automation/n8n/README.md). Apply migration `0023_n8n_service_actor.sql` locally, then run `Set-Item Env:N8N_ACTOR_PROVISION 'local-confirmed'` and `npm.cmd run n8n:actor:provision:local` from `server/` with a local PostgreSQL `DATABASE_URL`. The command returns a stable `N8N_ACTOR_ID` from `service_actors` and a PowerShell command to set it. It refuses production and remote targets and creates no password or human account. Clear the one-time confirmation variable after provisioning. Set `N8N_COD_ENABLED=1`, `N8N_SERVICE_TOKEN`, `N8N_WEBHOOK_SECRET`, `N8N_ACTOR_ID`, and `N8N_WEBHOOK_URL` on Server. Enabling COD without the required configuration fails startup. Production provisioning requires a separately reviewed process; this local command cannot run there. No secret values belong in source control.

For n8n callbacks, `order_events.actor_id` is null and `order_events.service_actor_id` references the dedicated machine identity. Corresponding immutable audit entries go to `service_audit_records`, which also references that identity. Human `accounts` roles, credentials, sessions, and audit attribution are unchanged.

Non-goals: online payment gateways, public webhook exposure, courier integration, SMS, delivery ETA, automated outbox scheduling, and live authenticated n8n verification. n8n never writes PostgreSQL or collects money on a timer.
